# A route from a MedExtract prototype to a shared test

## The product decision

The first user is the integration engineer who signs off a change to an OCR-to-FHIR or LIS-to-EHR pipeline. Give them a synthetic source, a small oracle they can review, a command their CI can call and an error they can locate on the original page. A capable reference implementation is helpful. The project's durable asset would be the set of independently adjudicated cases and their history. A company using Java, .NET or an entirely different extraction model should be able to contribute or replay them. [How to test a converter](../README.md) · [Existing FHIR and laboratory tools](ecosystem.md)

MedExtract already has printable Spanish lab reports, normalized labels, row and cell geometry and a released row-association scorer. Those artifacts let implementers inspect a failure at the boundary between a document and a structured clinical record. The current project adds a FHIR comparison and independent binding specification. It can be maintained without publishing the private clinical engine, model weights, prompts or a site's patient information. In the first release the 32 codes cover a small quantitative lab catalog. A single sample illustrated in a README and 100 deliberately difficult, reviewed cases would teach adopters more about failure modes than advertising 70,000 generated sheets alone. [Public generator](https://github.com/AdrianPerez3/medextract-lab-generator) · [Pinned starter dataset](https://huggingface.co/datasets/AdrianPerez3/medextract-synthetic-lab-reports-starter/tree/81da521d08425bd57922a1cf8bb17aa49d11b537)

| Option | Evidence and decision |
| --- | --- |
| Build another general PDF-to-FHIR service | Existing pathology converters already cover this workflow. Hospital deployment would add interface, support and local validation obligations before the shared testing asset reaches a second user. Keep the converter interface open to multiple implementations. [Lab2FHIR](https://github.com/is81/Lab2FHIR) |
| Build a universal LOINC mapper | Mapping requires specimen, timing, property, scale and sometimes method. NLM already has public validation/correction software. Use its findings to design cases, and version the evidence behind each mapping. [NLM implementation](https://github.com/LHNCBC/loinc-mapping-validation-correction) · [LOINC term axes](https://loinc.org/kb/users-guide/major-parts-of-a-loinc-term/) |
| Publish a source-to-FHIR regression suite | A converter team can use one case immediately and contribute one more when it finds a bug. Buyers can ask competing products to reproduce the same case. The main risk is circular scoring. Each expected answer and row binding needs provenance independent of the candidate's clinical values. [Measured comparator experiment](validation.md) |
| Launch a certification label | A trust mark would require independent governance, scoped criteria, terminology coverage, appeals and institutional acceptance. First make the evidence independently reproducible and let programs decide how to use it. [European Commission EHDS timeline](https://health.ec.europa.eu/ehealth-digital-health-and-care/european-health-data-space-regulation-ehds_en) · [US certification test kit](https://fhir.healthit.gov/test-kits/onc-certification-g10/) |

## Who gets value and what they can verify

| Audience | First task | Evidence of adoption |
| --- | --- | --- |
| OCR or clinical AI vendor | Run its existing extractor on the supplied image, propagate row IDs or supply an independently recorded manifest, and locate its first disagreement. | A second codebase runs the cases without changes to expected answers. It catches a defect that survives the team's usual validation. |
| Hospital, reference lab or LIS/EHR integration team | During a test-system upgrade, compare two exports of the same synthetic report. Reorder rows, repeat an analyte and amend one result. | A lab informatician reviews the expected answer, an interface engineer reproduces it, and the team retains the check in regression testing. |
| Researchers | Evaluate extraction and benchmark scoring separately. Stratify results by source layout, numerical punctuation, report length and missing facts. | A group publishes its fixture revision, configuration, unsupported denominator and attributable row-level failures. |
| Procurement teams, public interoperability programs and regulators | Ask for replayable synthetic evidence naming the guide, terminology environment and case definitions. Compare where each submitting system succeeds, fails or cannot be evaluated. | An independent test organizer can rerun the cases under its own rules. Formal acceptance and endorsement remain decisions for the relevant institution. |

## What to build next, in order

1. **Run a two-implementation pilot.** Pick one PDF-to-FHIR team and an independently maintained LIS or interface-engine team. Give both the same four cases: upper bound, adjacent equal-unit values swapped, repeated LOINC with distinct row IDs, and unknown specimen/status. Ask each to record its own row-to-resource trace. Classify time to first result, unsupported inputs and confirmed defects. Freeze the original cases and document changes to the expected answers. No participating sites or vendors have been confirmed.
2. **Publish a reviewed European lab document pack.** Have one lab informatician and an independent FHIR implementer review specimen, grouping, date semantics, terminology version, status and uncertainty for every released case. Include legitimate alternate representations and rationale. Validate each original candidate with a pinned R4 4.0.1 / EU Lab 2.1.0 toolchain and record terminology availability alongside its outcome. Start with a single attested numeric result, then repeated tests, nested panels, coded or absent results, amendments and documented reference intervals. Add handling for each only when both the source and receiver semantics have been reviewed. [European Laboratory Report guide](https://hl7.eu/fhir/laboratory/2.1.0/) · [Historical package-validation study](https://medinform.jmir.org/2024/1/e57569/)
3. **Make the same case useful to a second input format.** Add one fictional HL7 v2 ORU_R01 from an independently reviewed source and a second converter. Tie OBR/OBX grouping to the same result IDs. Test two panels sharing an analyte and a corrected result. This can reach LIS integration teams whose feed never contained a PDF. Select the concrete HL7 v2 version and local conventions with a pilot partner. [HL7 v2-to-FHIR mapping guide](https://hl7.org/fhir/uv/v2mappings/STU1/artifacts.html)
4. **Distribute where implementers already work.** Release the CLI, schema versions, issue templates and tagged examples on GitHub after review. Link the pinned Hugging Face dataset card to the CLI release and vice versa. Make the smallest test runnable from a checkout offline, then publish a Python package once installation and licensing have been reviewed. A frozen evaluated corpus and results can later receive a DOI. Take a reproduced, appropriately licensed fixture to the relevant HL7 Europe or IHE testing community. A project can earn a place in an implementer's CI before a public program formally references it. [IHE-Europe Plugathon](https://connectathon.ihe-europe.net/ihe-plugathon-2026)
5. **Add another jurisdiction or FHIR release when there is a receiver.** A US adopter can name the US Core version and specific API behavior it needs. A migration experiment can run the same oracle against R5/R6 output with a version-specific adapter and independent controls. Maintain per-version evidence and publish incompatibilities. [US Core published versions](https://hl7.org/fhir/us/core/package-list.json) · [HL7 core release ledger](https://hl7.org/fhir/package-list.json)

## What to measure before expanding

Count independent implementations that complete a run, teams that keep the test in CI after an upgrade and independently confirmed defects. For every technical result publish total reports, expected rows, evaluable rows, unsupported reports, missed and extra rows, wrong links, comparator losses, and false alarms after adjudication. Break out errors by category. Calculate uncertainty at the report or site level where appropriate. An extractor abstaining on difficult cases cannot improve its advertised score by silently shrinking the denominator. Track failing seeded examples and known-good cases separately. Keep synthetic and operational performance estimates distinct.

The current full replay counterchecks the local exporter and checker by planting known errors. The labeled-image sample adds independent visible evidence. Both still share the synthetic generator's assumptions about the underlying lab values and codes. The first external pilot should prioritize new input layouts, an independently derived expected answer and a second software implementation. Success is a repeatable defect found in a system its maintainer can actually fix.
