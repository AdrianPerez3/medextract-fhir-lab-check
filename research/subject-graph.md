# When every result matches but the subjects disagree

In the previous local preview, changing only the subject of the European teaching document's Composition to a second, explicitly bundled fictional Patient still produced a pass. The report, two Observations and serum Specimen continued to refer to the original fictional Patient. A reader using the document header would encounter a different subject from a reader following the report. All numeric rows were untouched. The new checker returns `subject-conflict` at `Composition.subject`. The test builds the second Patient in memory. ## Which references the tool can evaluate

| Candidate representation or change | Outcome |
| --- | --- |
| Omitted optional subject in a collection, with no competing assertion | The row comparison can proceed. It makes no assertion about the actual patient. |
| Same reference expressed relatively and absolutely under one REST base | The checker resolves both to a common address. Different service roots remain distinct. |
| Report and linked results carry external HTTP(S) subject references | Their addresses and available type evidence can be compared offline. Existence, the content of the referenced resource and real-world identity are unverified. An opaque external subject URL needs a declared type when the bundle supplies no target. |
| A subject references a missing URN target | The checker reports `unresolved-reference` for each affected field. Repeating the same unresolved URN across every row cannot produce a pass. A document must also include the directly referenced Composition subject. |
| An Observation declares Patient but points to a bundled Device, or a report uses a Specimen as its subject | The checker reports `subject-type-mismatch`. Specimen may reference a Substance as its own subject. R4 defines the allowed target types separately for each field. |
| Two linked specimens reference different subjects and neither row declares a subject | The single-subject consistency check reports `subject-conflict` at report scope. The report-wide finding leaves open which association needs correction. |
| An Observation references a serum Specimen marked `entered-in-error` | A matching serum code still yields `invalidated-specimen` on the affected source row. A consumed sample may carry `unavailable`. The checker treats physical availability and sample quality as outside its clinical assessment. |

FHIR's target types and role of subjects come from the resource definitions. A report and an Observation may describe a Patient, Group, Device or Location. A Specimen can additionally come from a Substance. Composition permits a wider range of subjects and sets the document context. R4 specifies the meaning of a declared resource type alongside a literal reference, and how readers should resolve bundle references. [Observation.subject](https://hl7.org/fhir/R4/observation-definitions.html#Observation.subject) · [DiagnosticReport.subject](https://hl7.org/fhir/R4/diagnosticreport-definitions.html#DiagnosticReport.subject) · [Specimen.subject](https://hl7.org/fhir/R4/specimen-definitions.html#Specimen.subject) · [Composition.subject](https://hl7.org/fhir/R4/composition-definitions.html#Composition.subject) · [Reference.type](https://hl7.org/fhir/R4/references-definitions.html#Reference.type) · [Bundle resolution](https://hl7.org/fhir/R4/bundle.html#references) · [Specimen status codes](https://hl7.org/fhir/R4/codesystem-specimen-status.html)

This comparison is for a single-subject laboratory fixture. A finding establishes a difference between candidate graph references. Establishing that two distinct referring systems identify the same person requires independent identity evidence. Maternal/fetal relationships, donor testing, pooled specimens, group membership and patient-merge histories need dedicated reference cases before they can be scored. The checker makes no network requests, and its findings return a field, a code and an attested row ID when available. The synthetic controls also verify that these findings omit the target identifiers.
